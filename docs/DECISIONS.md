# Rust-Cert-Scan: принятые решения

Дата фиксации: 2026-11-11.

Документ закрывает открытые вопросы из `docs/ARCHITECTURE.md` (раздел 10.4) и таблицу «Решения, блокирующие задачи» из `docs/PLAN.md`. При расхождении с этими документами приоритет у решений ниже.

## D-09. Зависимости с лицензией строго Apache-2.0

- Вопрос: следствие D-01, возник при настройке `deny.toml` (P0-03).
- Решение: `Apache-2.0` оставлена в списке разрешённых лицензий `deny.toml`, потому что большинство крейтов экосистемы Rust имеют двойную лицензию `MIT OR Apache-2.0` и используются на условиях MIT. Лицензия Apache-2.0 без альтернативы формально несовместима с GPLv2 (позиция FSF), и cargo-deny такой случай не отличает. Поэтому перед распространением бинарников каждую зависимость с лицензией строго `Apache-2.0` (без `OR MIT` или другой GPLv2-совместимой альтернативы) надо проверять вручную и либо заменять, либо получать отдельное заключение о допустимости.
- Кто принял: оркестратор.
- Разблокирует: P0-03. Ручная проверка — обязательный шаг перед P4-14 (релизные сборки).

## D-10. `unsafe_code = "forbid"` на весь workspace

- Дата: 2026-11-11.
- Вопрос: расхождение между ARCH, раздел 9, и P0-01 («`forbid` в пяти крейтах, `deny` в остальных») и фактической настройкой `[workspace.lints.rust]` в корневом `Cargo.toml`.
- Решение: `unsafe_code = "forbid"` действует на весь workspace, без деления на крейты с `forbid` и крейты с `deny`. Точечное исключение возможно только отдельным решением в этом документе с переводом конкретного крейта с `[lints] workspace = true` на собственный блок `[lints]`.
- Граница: крейт `fuzz/` в workspace не входит (`exclude = ["fuzz"]`) и workspace-lints не наследует; `#![no_main]` и экспорт символа без искажения имени, в который раскрывается макрос `fuzz_target!`, допустимы только внутри `fuzz/`.
- Кто принял: пользователь.
- Разблокирует: ничего не блокировал; уточняет приёмку P0-01 и требования безопасности ARCH, раздел 9.

## D-11. Kx=any (TLS 1.3) считается forward secrecy на уровне таблицы

- Дата: 2026-11-11.
- Вопрос: как классифицировать suites TLS 1.3, у которых в `cipher-mapping.txt` обмен ключами записан как `Kx=any` (P1-02, `CipherInfo::has_forward_secrecy`).
- Решение: на уровне таблицы `tls-data` значение `Kx=any` считается forward secrecy. Режим `psk_ke` (PSK без (EC)DHE), при котором forward secrecy нет, таблица не различает; его уточняет проверка P1-20.
- Кто принял: пользователь.
- Разблокирует: ничего не блокировал; уточняет выход P1-02 и объём P1-20.

## D-12. Имя `extended_master_secret` в API при `extended_main_secret` в реестре IANA

- Дата: 2026-11-11.
- Вопрос: снимок реестра IANA (`crates/tls-data/data/iana/tls-extensiontype-values-1.csv`) называет расширение с кодом 23 `extended_main_secret`, а RFC 7627, testssl.sh и существующие реализации — `extended_master_secret`. Какое имя использовать в API `tls-probe`.
- Решение: в API `tls-probe` используется имя из RFC 7627: `kind::EXTENDED_MASTER_SECRET`, `Extension::extended_master_secret()`, `ServerExtension::ExtendedMasterSecret`. Имя из реестра IANA (`extended_main_secret`) доступно через `tls-data` по коду расширения и используется там, где выводится имя по реестру. Оговорка продублирована в `crates/tls-probe/src/server_hello.rs` и `crates/tls-probe/src/ext/raw.rs`.
- Кто принял: пользователь (ревью P1-03 – P1-06).
- Разблокирует: ничего не блокировал; закрепляет именование для P1-06 и проверок, которые выводят расширения.

## D-13. Декодер: распознавание HelloRetryRequest, пустые записи, лимиты потока

- Дата: 2026-11-11.
- Вопрос: находки ревью P1-04 – P1-06: второй ServerHello после HelloRetryRequest терялся, если вызывающий код вызывал `resume_plaintext()` раньше, чем декодер читал ChangeCipherSpec; поток пустых записей и общий объём потока ничем не ограничивались.
- Решение:
  - декодер сам распознаёт HelloRetryRequest по полю `random` сообщения `server_hello` и ждёт второй ServerHello: ChangeCipherSpec в этом состоянии отдаётся событием, но режим `Opaque` не включает. Ожидание заканчивается на следующем `server_hello`, который HRR не является. Второй HRR подряд ошибкой декодера не считается, число HRR проверяет вызывающий код. `resume_plaintext()` остаётся ручным переопределением, вызывать его после HRR не требуется;
  - пустая запись `handshake` — ошибка `ParseError::InvalidValue` (RFC 8446, раздел 5.1; RFC 5246, раздел 6.2.1);
  - пустая запись `alert` — ошибка `ParseError::InvalidValue` (RFC 5246, раздел 6.2.1); событие `Alert` выдаётся на каждые два байта потока alert, в том числе собранные из двух записей;
  - `ParseLimits::max_total_bytes` — общий объём потока, по умолчанию 1 МиБ (1 048 576 байт); превышение — `ParseError::LimitExceeded`;
  - `ParseLimits::max_empty_records` — число подряд идущих пустых записей типов `application_data`, `heartbeat`, неизвестного типа и любых записей в режиме `Opaque`, по умолчанию 16; превышение — `ParseError::LimitExceeded`.
- Граница: оба значения по умолчанию предварительные. В ARCH, раздел 5, «общий объём чтения на соединение» назван без числа; значения уточняются, когда появятся разбор Certificate с настраиваемым лимитом (P1-07) и сетевое чтение через `Decoder` (P1-11).
- Кто принял: пользователь (ревью P1-03 – P1-06); числовые значения предложены при исправлении находок и ждут подтверждения.
- Разблокирует: ничего не блокировал; уточняет выход P1-04 и P1-06.

## D-14. Декодер не включает режим Opaque по факту ServerHello TLS 1.3

- Дата: 2026-11-11.
- Вопрос: находка сверки P1-04 – P1-06. В записанном обмене с HelloRetryRequest (фикстура `tls13-serverhello-openssl-basic-after-hrr`) OpenSSL шлёт ChangeCipherSpec один раз, сразу за HRR; после второго ServerHello CCS нет, и первая зашифрованная запись приходит событием `Event::ApplicationData`, а не `Event::Opaque`. Тест объединял оба события в один вариант и это скрывал; doc-комментарий `decoder.rs` описывал CCS после второго ServerHello, которого в записи нет.
- Решение: декодер `tls-probe` не переводит поток в режим `Opaque` по факту ServerHello с согласованной версией TLS 1.3. Режим `Opaque` включает только ChangeCipherSpec (с исключением для CCS между HRR и вторым ServerHello, D-13). Зашифрованные записи после ServerHello TLS 1.3 поэтому приходят либо как `Opaque` (сервер прислал CCS в режиме совместимости с middlebox), либо как `ApplicationData` (CCS после ServerHello не было: сервер без режима совместимости или обмен с HRR у OpenSSL). Трактовать любую запись `application_data` после ServerHello TLS 1.3 как шифртекст обязан вызывающий код: `net` (P1-11) и `tls-session` (P1-21).
- Обоснование: декодер не согласует версию — итоговая версия определяется разбором ServerHello (`supported_versions`), который выполняет вызывающий код через `ServerMessage`; повторять этот разбор внутри декодера значит дублировать логику и менять поведение на TLS-путях, уже покрытых фикстурами. Запись `application_data` до CCS декодер и раньше отдавал как `ApplicationData`.
- Граница: поведение декодера не менялось. Исправлены doc-комментарий `crates/tls-probe/src/decoder.rs` (описаны оба случая: с CCS и без него) и тест `hello_retry_exchange_without_manual_resume`, который теперь сравнивает точный вариант события и длину тела записи (`ApplicationData`, 51 байт).
- Кто принял: пользователь (сверка P1-04 – P1-06).
- Разблокирует: ничего не блокировал; уточняет контракт `Decoder` для P1-11 и P1-21.

## D-15. Лимиты сообщения Certificate: число сертификатов и размер одного сертификата

- Дата: 2026-11-11.
- Вопрос: P1-07 требует лимитов на число сертификатов в сообщении Certificate и на размер одного сертификата; числовых значений для них в `docs/ARCHITECTURE.md` нет.
- Решение:
  - `ParseLimits::max_certificates` — наибольшее число сертификатов в одном сообщении Certificate, по умолчанию 32 (`DEFAULT_MAX_CERTIFICATES`); превышение — `ParseError::LimitExceeded`;
  - `ParseLimits::max_certificate_len` — наибольшая длина одного сертификата (DER), по умолчанию 32 КиБ (32 768 байт, `DEFAULT_MAX_CERTIFICATE_LEN`); превышение — `ParseError::LimitExceeded`. Заявленная длина сравнивается с лимитом до чтения тела сертификата;
  - пустой список сертификатов — корректный результат разбора, а не ошибка; сертификат нулевой длины внутри списка — `ParseError::InvalidValue`.
- Обоснование: цепочки публичных серверов состоят из 2 – 5 сертификатов размером 1 – 3 КиБ каждый; сертификаты с постквантовыми ключами и подписями занимают до 10 – 20 КиБ. Значения оставляют запас и при этом меньше `max_handshake_len` (64 КиБ), который декодер применяет раньше: сообщение Certificate крупнее 64 КиБ отвергается ещё при сборке.
- Граница: оба значения предварительные. Уточняются вместе с `max_handshake_len`, когда появятся разбор X.509 (`x509-check`, P1-22) и сетевое чтение через `Decoder` (P1-11): цепочка, которая не помещается в 64 КиБ, потребует поднять лимит сообщения, а не только лимит сертификата. Формат Certificate TLS 1.3 (`certificate_request_context`, расширения записей) эти лимиты пока не использует — его разбор остаётся задаче P1-21.
- Кто принял: значения предложены при выполнении P1-07; подтверждено оркестратором 2026-11-11.
- Разблокирует: P1-07 (`CertificateList::parse`).

## D-16. SSLv2: отдельный декодер ответа, только двухбайтовый заголовок записи

- Дата: 2026-11-11.
- Вопрос: P1-08. Основной `Decoder` на ответ SSLv2-сервера возвращает `ParseError::NotTls`; вызывающему коду, который отправил SSLv2 CLIENT-HELLO, нужен путь разбора ответа, а поведение `Decoder` на TLS-путях менять нельзя. В плане не сказано, в каком объёме разбирать трёхбайтовый заголовок записи с padding и какие лимиты применять.
- Решение:
  - ответ на SSLv2 CLIENT-HELLO разбирает отдельный тип `tls_probe::sslv2::Sslv2Decoder` (`feed(&mut &[u8]) -> Result<Sslv2Event<'_>, ParseError>`); `Decoder` не изменён и по-прежнему возвращает `NotTls` на SSLv2-ответ;
  - `Sslv2Decoder` принимает только записи с двухбайтовым заголовком (старший бит первого байта установлен). Трёхбайтовый заголовок (padding, security escape) разбирает функция `Sslv2RecordHeader::parse`, но декодер такую запись не принимает: padding есть только у зашифрованных записей с блочным шифром, а открытая часть handshake (SERVER-HELLO, ERROR) идёт без него;
  - если ответ начинается с TLS-записи (тип содержимого 20 – 24, старший байт версии 3), декодер возвращает `Sslv2Event::TlsReply` с двумя забранными байтами — это и есть результат «SSLv2 не поддерживается»; событие окончательное, повторный вызов вход не забирает. Любое другое начало с нулевым старшим битом — `ParseError::NotTls`;
  - новых полей в `ParseLimits` нет: длина записи проверяется по `max_record_len` (18 432 при допустимых форматом 32 767), общий объём — по `max_total_bytes`, сертификат в SERVER-HELLO — по `max_certificate_len`; запись нулевой длины — `ParseError::InvalidValue`;
  - ограничения спецификации на значения (CHALLENGE 16 – 32 байта, SESSION-ID 0 или 16, CONNECTION-ID 16 – 32, нулевые поля при SESSION-ID-HIT) не проверяются ни при сборке, ни при разборе: пробнику нужно уметь отправить нестандартный hello и увидеть нестандартный ответ. Длина CIPHER-SPECS, не кратная трём, — `ParseError::InvalidValue`.
- Обоснование: формат сверен с draft-hickman-netscape-ssl-00 (разделы 4.1, 5.5.1, 5.6.1, 5.7.1, приложение C). Двухбайтовый заголовок всегда начинается с байта `0x80` и выше, типы содержимого TLS меньше `0x80`, поэтому различение SSLv2 и TLS по первому байту однозначно.
- Граница: решение о двухбайтовом заголовке принято без записей реальных серверов — стенд на OpenSSL 4.1.0 SSLv2 не поддерживает, все тесты синтетические. Пересматривается, когда появятся фикстуры с docker-стенда со старым OpenSSL (P1-28): если сервер шлёт открытый SERVER-HELLO с трёхбайтовым заголовком, декодер придётся расширить.
- Кто принял: предложено при выполнении P1-08; подтверждено оркестратором 2026-11-11.
- Разблокирует: P1-08; уточняет контракт для P1-18 (проверка протоколов) и P1-11.

## D-17. Крейт net: таймауты, DNS-кэш, перебор адресов, буфер чтения и закрытие соединения

- Дата: 2026-11-11.
- Вопрос: P1-10 и P1-11. В `docs/ARCHITECTURE.md` названы раздельные таймауты connect, handshake и read, общий дедлайн, DNS-кэш с TTL и отрицательным кэшем, но числовых значений нет; не определены порядок перебора адресов цели, размер буфера чтения и способ закрытия соединения после пробы.
- Решение:
  - таймауты по умолчанию (`net::Timeouts`): connect — 5 с на один адрес, handshake (от отправки пробника до первого байта ответа) — 10 с, read (между порциями ответа) — 5 с, write (отправка пробника целиком) — 5 с, общий дедлайн обмена на одном соединении — 30 с. Каждое чтение и каждая запись ограничены остатком до общего дедлайна; дедлайн проверки (`--check-timeout`) вызывающий код задаёт через `ProbeSession::set_deadline`, действует более ранний;
  - DNS-кэш (`net::DnsCacheConfig`): 1024 записи, время жизни успешного ответа — 300 с, отрицательного (ошибка резолвера, таймаут, пустой ответ) — 30 с, таймаут одного обращения к резолверу — 5 с. Резолвер — системный, через `tokio::net::lookup_host`, без отдельного DNS-крейта; системный резолвер TTL не отдаёт, поэтому время жизни задаётся конфигурацией. Имя сравнивается без учёта регистра ASCII. Параллельные запросы одного имени ждут один резолв. При переполнении удаляются истёкшие записи, затем запись с самым ранним сроком истечения;
  - режимы разрешения (`net::ResolveOptions`): семейство адресов `Any`, `V4Only` (`-4`), `V6Only` (`-6`); `DnsMode::Disabled` (`--dns none`) — резолвер не вызывается, цель должна быть IP-литералом или иметь IP override; IP override (`--ip <addr>`) — соединение с заданным адресом, исходное имя сохраняется для SNI. IP-литерал и IP override резолвер не вызывают; несовпадение с разрешённым семейством — ошибка `DnsError::FamilyMismatch`;
  - перебор адресов: в порядке резолвера (системный резолвер уже упорядочил их по RFC 6724), последовательно, не более 4 адресов на один вызов `Connector::connect` (`ConnectorConfig::max_addresses`), на каждый адрес — свой таймаут connect; первое открытое соединение возвращается. Параллельных попыток (Happy Eyeballs) нет: сканер не открывает соединений сверх учтённых. Класс ошибки `ConnectError::class` для нескольких попыток берётся по последней;
  - счётчики (`net::ConnStats`): число попыток, число открытых соединений и суммарное время connect; области образуют дерево (`child()`), соединение учитывается в своей области и во всех предках — так JSON получает `connections` и на проверку, и на цель;
  - буфер чтения обмена — 16 КиБ (`net::probe_io::READ_BUFFER_LEN`), один на соединение, переиспользуется между чтениями; `BytesMut` и пул буферов на хост (ARCH, раздел 6.5) не используются;
  - признак шифртекста в обмене (применение D-14): запись считается шифртекстом, если она пришла событием `Opaque` после ChangeCipherSpec либо событием `ApplicationData` после ServerHello, не являющегося HelloRetryRequest. Версию `net` не согласует;
  - ошибка записи пробника из-за ошибки ввода-вывода не прекращает обмен: ответ читается, так как сервер мог прислать alert или текст и закрыть соединение; сведения об ошибке остаются в `ProbeTranscript::write_failure`. Таймаут записи обмен прекращает;
  - закрытие после пробы: `shutdown` стороны записи (FIN) с ограничением 250 мс (`net::timeouts::CLOSE_TIMEOUT`), затем сокет отпускается; ответа сервера не ждём. `close_notify` не отправляется; `SO_LINGER 0` не ставится.
- Обоснование: значения таймаутов — того же порядка, что у testssl.sh (`--connect-timeout`, `--openssl-timeout`), и с запасом для медленных серверов; отрицательный TTL короче положительного, чтобы временный сбой резолвера не выключал цель на весь скан. `close_notify` открытым текстом после ServerHello TLS 1.3 был бы нарушением протокола (alert обязан быть зашифрован), а ключей у пробника нет; RST вместо FIN выглядит для сервера и IDS как обрыв.
- Граница: все числовые значения предварительные и калибруются вместе с лимитами движка (P1-12, P4-03). Режимы `--ip one|all` и `--dns full|min` из ARCH, раздел 7.1, не реализованы: P1-10 требует только `--ip <addr>` и `--dns none`. Proxy и STARTTLS — Фаза 3; точка расширения — обобщённый по транспорту `net::Conn<S>` и обмен поверх любого `AsyncRead + AsyncWrite`. Таймаут резолва не отменяет сам вызов `getaddrinfo` в блокирующем пуле tokio — отменяется только ожидание.
- Кто принял: предложено при выполнении P1-10 и P1-11; подтверждено оркестратором 2026-11-11 как предварительное, переопределяется конфигом (P1-25, P1-26).
- Разблокирует: P1-10, P1-11; уточняет контракт для P1-12 (разрешение на соединение берётся до вызова `Connector::connect`), P1-17 (ранний выход по `ConnectErrorClass` и `StopReason`) и P1-26 (значения по умолчанию для флагов таймаутов).

## D-18. Ключ лимита «на хост» — IP-адрес соединения

- Дата: 2026-11-11.
- Вопрос: P1-12. В ARCH 6.1 семафор на хост назван «IP:port»; имя цели и адрес соединения могут не совпадать (виртуальные хосты, CDN, несколько портов одного сервера).
- Решение: ключ состояния хоста в `engine::limits` (семафор соединений, token bucket, AIMD, circuit breaker) — IP-адрес, на который фактически идёт соединение, без порта и без имени. Несколько имён и несколько портов на одном адресе делят один лимит и одну скорость.
- Обоснование: лимит защищает сервер, а сервер определяется адресом; ключ по имени или по паре адрес-порт умножал бы нагрузку на одну машину на число имён или портов.
- Граница: слот параллельно сканируемых хостов (`--max-hosts`) берётся на каждую цель, а не на адрес: две цели на одном адресе занимают два слота хостов, но делят состояние. Состояние хоста (в том числе отключение breaker'ом) живёт, пока с адресом идёт работа; цель на тот же адрес, пришедшая позже, начинает с чистого состояния.
- Кто принял: оркестратор (требование задачи P1-12), 2026-11-11.
- Разблокирует: P1-12, P1-13; уточняет контракт для P1-17 (планировщик вызывает `Limiter::host` с адресом, а не с именем).

## D-19. Лимиты: порядок захвата, значения по умолчанию, jitter, защита сканирующей машины

- Дата: 2026-11-11.
- Вопрос: P1-12. В ARCH 6.1 порядок захвата — «глобальный rate → rate хоста → семафор хоста → глобальный семафор», burst не задан, источник случайности для jitter не определён.
- Решение:
  - единая точка — `engine::limits::Limiter`: `Limiter::host(addr) -> HostHandle` (слот хостов, один раз на цель), `HostHandle::acquire() -> Result<Permit, Denied>`, `Permit::report(outcome)`. `net::Connector` лимитов не содержит: разрешение берётся до `Connector::connect` (D-17);
  - порядок захвата: слот хостов → слот соединений хоста → решение breaker'а → токен хоста → глобальный токен → задержка (пауза backoff плюс jitter) → глобальный слот соединений → повторное решение breaker'а. Токены берутся после слота хоста, иначе задача забирала бы токен задолго до соединения, пока стоит в очереди хоста. Глобальный слот — последним: ожидание токена медленного хоста не удерживает общую ёмкость. Взаимной блокировки нет: порядок един для всех задач, а владелец глобального слота больше ничего не ждёт;
  - значения по умолчанию (`LimitsConfig`): соединения — по D-04 (64 глобально, 2 на хост, 16 хостов; пресет `gentle` — 1 на хост); скорости и jitter — по ARCH 6.1 (200 и 10 соединений в секунду, jitter 0–50 мс); burst — 16 глобально и 2 на хост (предварительные). «Без ограничения» — `Rate::Unlimited` для скоростей и `limits::UNLIMITED` для числа соединений и хостов;
  - rate limit — GCRA (эквивалент token bucket) на `tokio::time`, скорость в тысячных соединения в секунду;
  - jitter — собственный генератор SplitMix64 за trait'ом `JitterSource`, seed из системных часов либо внедряемый; внешний крейт не нужен: генератор занимает десять строк, криптостойкость не требуется;
  - отмена ожидания ничего не теряет: слоты освобождаются при drop, выданные токены возвращаются, пробное соединение half-open возвращается breaker'у;
  - состояние хоста создаётся лениво и удаляется вместе с последней ссылкой (`HostTable` хранит слабые ссылки): размер таблицы равен числу активных хостов;
  - счётчики — `LimitStats`: дерево областей по образцу `net::ConnStats` (область хоста — потомок области скана), по этапам ожидания: число срабатываний и суммарное время;
  - защита сканирующей машины (`GuardConfig`): исход `LocalExhaustion` (EMFILE, ENFILE по коду ОС; `AddrNotAvailable`, `OutOfMemory` по `io::ErrorKind`) делит глобальный лимит соединений на 2, не чаще раза в 1 с и не ниже 4; каждые 32 исхода без такой ошибки лимит растёт на 4 до настроенного (предварительные значения).
- Граница: «глобальный контур» из ARCH 6.2 (рост доли таймаутов по всем хостам снижает глобальный rate) не реализован: реализована защита по нехватке локальных ресурсов; точка расширения — `Shared::feedback`, куда приходит реакция на каждый исход. CLI и TOML — P1-25, P1-26.
- Кто принял: предложено при выполнении P1-12, ждёт подтверждения оркестратора.
- Разблокирует: P1-12; уточняет контракт для P1-17 и P1-26.

## D-20. Backoff и circuit breaker: классификация исходов и значения по умолчанию

- Дата: 2026-11-11.
- Вопрос: P1-13. ARCH 6.2 называет сигналы и схему AIMD без чисел; не определено, как трактовать EOF до первого байта и отказ в соединении.
- Решение:
  - классификация — в одном месте, `engine::limits::Outcome::signal` (таблица в документации `limits::backoff`). Успех — только выполненное условие обмена. Нейтральные (не запускают backoff, прерывают серию неуспехов): fatal alert, EOF на границе сообщений, ошибка разбора, превышение лимита разбора, общий дедлайн. Перегрузка: сброс, таймауты connect, handshake и read, EOF посреди сообщения, ошибка записи и чтения, недостижимость, прочие ошибки connect;
  - EOF до первого байта неоднозначен: первые два подряд нейтральны (так старые стеки отвечают на неподдерживаемый hello), начиная с третьего подряд каждый — неуспех; пробное соединение half-open с таким EOF — неуспех сразу;
  - отказ в соединении до первого установленного — закрытый порт (ранний выход, причина `unreachable`), после — перегрузка; не-TLS ответ до первого ответа TLS — ранний выход (`not_tls`), после — нейтрален; неразрешившееся имя — ранний выход (`unresolved`). Повторов перед ранним выходом — ноль (ARCH 6.3);
  - AIMD (`AimdConfig`): при перегрузке лимит соединений и скорость хоста делятся на 2 (не ниже 1 соединения и 1 соединения в секунду), задержка перед соединением — 250 мс и удваивается до 10 с; каждые 8 успехов подряд — плюс 1 соединение и плюс 1 соединение в секунду до настроенного максимума, задержка делится на 2 и обнуляется ниже 250 мс;
  - breaker (`BreakerConfig`): 5 неуспехов подряд размыкают; пауза 5 с, далее удваивается до 60 с; после паузы — одно пробное соединение; ответ сервера (успех или нейтральный исход) замыкает и обнуляет счёт циклов; после 3 размыканий подряд следующее отключает хост с причиной `blocked_or_down`;
  - решение для вызывающего — `Denied::Wait(пауза)` либо `Denied::Disabled(причина)`; `HostHandle::acquire_waiting` пережидает паузы сам.
- Граница: все числа предварительные, калибровка — P4-03. Нехватка локальных ресурсов хост не штрафует (D-19).
- Кто принял: предложено при выполнении P1-13, ждёт подтверждения оркестратора.
- Разблокирует: P1-13; уточняет контракт для P1-17 (статусы `unreachable`, `not_tls`, `blocked_or_down`, `not_tested`).

## D-21. Поток целей: формы записи, CIDR, файл, обратное давление

- Дата: 2026-11-11.
- Вопрос: P1-14. Не определены предел размера сети, обращение с адресом сети и широковещательным, IDNA, формат ошибок и способ обратного давления.
- Решение:
  - формы записи: имя, имя:порт, IPv4, IPv4:порт, `[IPv6]`, `[IPv6]:порт`, IPv6 без скобок, URL `https://` (путь и запрос сохраняются в `ScanTarget::path`), сети `адрес/префикс` и `адрес/префикс:порт`; порт по умолчанию 443;
  - имена — ASCII и punycode как есть; имена не в ASCII отклоняются с подсказкой про punycode: IDNA план не требует, зависимость не добавляется;
  - CIDR: биты хоста в записи обнуляются; выдаются все адреса по возрастанию, включая адрес сети и широковещательный; предел — 2^20 адресов на сеть (`DEFAULT_MAX_CIDR_ADDRESSES`, предварительное), настраивается; перебор — итератор-счётчик без материализации;
  - файл: запись на строку, комментарий `#` в начале строки или после пробела, LF и CRLF, BOM отбрасывается, предел длины строки 4096 байт, номер строки в ошибках; ошибочная строка — `OnError::Skip` (по умолчанию: ошибка отдаётся потребителю, чтение продолжается) либо `OnError::Stop`;
  - поток — `TargetStream` с методом `next()`: производитель в отдельной задаче резервирует место в ограниченном канале (64 элемента по умолчанию) перед каждой целью; trait `Stream` не реализован, чтобы не добавлять зависимость;
  - `--sni` и `--ip` применяются ко всем целям потока (`TargetOptions`); `ScanTarget::to_net` даёт `net::Target`, адрес `--ip` передаётся через `ScanTarget::resolve_options`, имя SNI — `ScanTarget::server_name`.
- Граница: дедупликации и перемешивания нет (план не требует); STARTTLS-протокол в строке файла, nmap и MX — Фаза 3; чтение stdin — через `TargetStream::from_reader`, подключение в CLI — P1-26.

- Разблокирует: P1-14; уточняет контракт для P1-17 и P1-26.
